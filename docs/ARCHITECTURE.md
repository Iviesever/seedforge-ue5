# Architecture

## Design goal

SeedForge makes the difficult parts independently reviewable: deterministic topology, validation, asynchronous ownership, and UE scene application are separate units with narrow interfaces.

## Component map

### `FSeedForgeGenerator`

Input is only `uint64 Seed` plus `FSeedForgeConfig`. A fixed SplitMix64 implementation proposes bounded integer room rectangles. Accepted rooms are sorted by minimum coordinate and size. Consecutive canonical room centers receive an L-shaped corridor whose bend orientation comes from the same explicit RNG stream.

The entrance is the first canonical room center. The exit is the room center with greatest Manhattan distance, with canonical iteration order providing the tie break. Room/corridor data is sorted before hashing.

### `FSeedForgeLayout`

The layout stores ordered rooms, ordered corridor cells, entrance, exit, source seed, and canonical hash. `GetCanonicalWalkableCells` expands rooms, appends corridors, sorts by Y/X, and removes duplicates.

The result is mutable as a C++ value type, but callers treat a successful result as immutable. Scene code receives it by const reference.

### `FSeedForgeValidator`

Validation deliberately fails in a deterministic order:

1. Room count matches the configuration.
2. Room rectangles and corridor cells are in bounds.
3. Room rectangles do not overlap.
4. Entrance and exit are walkable.
5. A four-neighbor breadth-first traversal reaches every walkable cell.

`TSet` is used only for membership/visited queries. No iteration over a set controls output ordering or hashing.

### `FSeedForgeAsyncCoordinator`

`Start` is called on the Game Thread. It cancels the previous token, assigns a monotonic request id, and launches the supplied pure work with `UE::Tasks::Launch`. The worker captures only shared lifetime state, an atomic cancellation token, move-only work/apply functions, and value inputs.

After work completes, `AsyncTask(ENamedThreads::GameThread, ...)` performs four gates before invoking Apply:

1. Shared coordinator state still exists.
2. Coordinator has not shut down.
3. Request token is not cancelled.
4. Request id is still the active id.

This implements newest-request-wins without blocking the Game Thread. Cancellation is cooperative suppression: already-running generation may finish CPU work, but its result cannot apply.

### `USeedForgeWorldSubsystem`

The subsystem lazily owns the coordinator. It captures itself through `TWeakObjectPtr` at the apply boundary, broadcasts only on the Game Thread, clears delegates during `Deinitialize`, shuts down the coordinator, and releases it.

### `FSeedForgeVisualizationPlanner` and `ASeedForgePreviewActor`

The planner converts canonical walkable cells into deterministic floor and exterior-wall transforms. Shared edges never emit walls. The Actor consumes the plan with two HISM components and the Engine cube asset. It does not alter topology.

The actor reads optional command-line values, requests generation through the subsystem, validates before applying, logs observable metrics, and can capture a screenshot before requesting a clean process exit.

### Demo module and scripts

`ASeedForgeDemoGameMode` supplies an engine default free-fly pawn, fixed capture camera, and runtime-created lighting. The only project-owned map is generated by `Scripts/CreateDemoMap.py`; no Blueprint is required.

PowerShell entry points call the installed binary UE 5.8 toolchain and store timestamped local evidence.

## Complexity

- Room placement: `O(A * R)`, where `A` is the explicit attempt budget and `R` is accepted rooms.
- Room overlap validation: `O(R^2)`.
- Walkable expansion and sorting: `O(W log W)`.
- Connectivity validation: expected `O(W)` membership/traversal after canonical cells are built.
- Canonical hashing: `O(R + C)` for rooms and corridor cells.

The current corridor `AddUnique` path is intentionally simple and can approach quadratic behavior in corridor-cell count. The scoped 48x48 demo is small; a production-scale version would use a membership bitmap while preserving sorted output.

## Determinism boundary

Guaranteed and tested:

- same SeedForge algorithm/plugin version;
- same `FSeedForgeConfig` values;
- same Win64 target and UE 5.8 toolchain;
- no global randomness, time, UObject state, or unordered output iteration.

Not guaranteed:

- future algorithm versions;
- another UE/compiler/platform integer or serialization model;
- identical scene render pixels across GPUs/drivers;
- cancellation at a precise instruction inside the pure generator.
